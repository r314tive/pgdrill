# pgdrill v1.0 Release Contract

Status: target contract. This document defines the intended GA boundary; it is
not a release date or a claim that the current prerelease already satisfies the
listed support gates.

## Meaning Of v1.0

`v1.0.0` is the first stable, self-managed recovery-assurance product release.
It must let an operator define, execute, inspect, and automate real PostgreSQL
restore drills without a hosted service.

The release is CLI-first. A web UI, multi-tenant SaaS, and a distributed
controller are not required for GA. They may consume the same stable contracts
later, but they cannot become alternate restore implementations.

## Required Product Surface

### Stable Engine And CLI

- One immutable drill attempt covers discovery, selection, provider
  validation, restore, PostgreSQL startup, required checks, evidence, policy,
  cleanup, and terminal reporting.
- Strict validation and read-only preflight happen before repository or target
  mutation.
- Direct `doctor`, `catalog`, `run`, `target`, and `report` commands remain
  usable from cron, CI, Kubernetes Jobs, and incident runbooks without a
  daemon.
- Cancellation, command deadlines, bounded evidence, redaction, operation
  checkpoints, unknown-outcome reconciliation, and owned cleanup are
  fail-closed.
- An uncatchably interrupted local attempt can be planned and reconciled
  without provider-command replay. Apply requires the exact reviewed digest,
  explicit stopped-executor confirmation, exact ownership cleanup, immutable
  preservation of incomplete history, and a new attempt ID for retry.
- Stable automation exit codes distinguish success, invalid input, operational
  failure, and cancellation. Structured report status and failure stages
  distinguish preflight, execution, policy, cleanup, and report-persistence
  outcomes.

### Recovery Capabilities

- Latest recovery and timestamp PITR are proven by real drills for every
  provider/version cell advertised with those capabilities.
- Backup selection rejects base backups that cannot satisfy the requested
  timestamp boundary before restore mutation.
- At least one post-backup WAL transaction must be replayed for latest-recovery
  evidence.
- Timestamp PITR evidence must prove both sides of the boundary: a transaction
  committed before the requested time is present and a later transaction is
  absent.
- Required probes cover PostgreSQL readiness, an operator-defined SQL
  assertion, `pg_amcheck`, and schema-only `pg_dump`. `pg_verifybackup` remains
  available where the restored artifact and provider make it applicable.
- RTO, RPO, backup-age, recovery-target, and cleanup verdicts remain typed,
  explicit, and fail-closed when required proof is missing.

### Supported Providers And Targets

The intended GA provider set is:

- WAL-G
- Barman
- pgBackRest
- pg_probackup

The intended GA target set is:

- an owned local PostgreSQL restore target
- an owned disposable CloudNativePG restore target using the Barman Cloud
  Plugin; retained native `barmanObjectStore` observations are legacy
  compatibility cells, not the forward-looking GA baseline

Implementation alone is insufficient. A provider or target is supported only
for the exact versions, platforms, repository topology, backup mode, and
recovery target recorded as field evidence in
[`compatibility/matrix.yaml`](../compatibility/matrix.yaml).

Before GA:

- every advertised provider has field evidence on at least two supported
  PostgreSQL major versions;
- every advertised `latest` or `timestamp` capability has two consecutive
  passed drills from the exact release candidate;
- Linux amd64 is covered for every advertised provider and target;
- WAL-G has at least one S3-compatible object-storage observation;
- CNPG Barman Cloud Plugin recovery has object-storage-backed observations,
  post-backup WAL replay, and explicit cleanup proof from the exact release
  candidate;
- any advertised CNPG version uses its supported backup/recovery API; versions
  beyond the native `barmanObjectStore` lifecycle require separately exercised
  Barman Cloud Plugin support;
- untested combinations remain visibly unclaimed rather than inferred from
  fixture or adjacent-version results.

The retained `v0.3.0-alpha.10` provider evidence now proves latest and
timestamp recovery on Linux amd64 through Docker emulation for all four native
providers. It closes a functional architecture gap, not the final-candidate,
native-hardware, or repeated-run gates above. The
retained `v0.3.0-alpha.12` Linux arm64 WAL-G/MinIO evidence separately closes
the existence of one S3-compatible observation. The retained
`v0.3.0-alpha.14` Linux arm64 evidence closes the existence of a second
PostgreSQL-major latest/timestamp point for all four native providers. These
observations do not replace the exact final-candidate, native Linux amd64,
published-artifact, remote-topology, pilot, or repeated-run requirements.

### Planning And Local History

- A daemon-free planner validates typed sources, target pools, probe profiles,
  recovery policies, and drill sets without infrastructure mutation.
- Planner output contains bounded expansion, concrete placement, immutable
  revisions, mutation count, and rejection reasons without resolved secrets.
- A local durable history stores immutable run specs, ordered events, terminal
  reports, and bounded artifact references.
- Operators can list, fully verify, inspect, import, and digest-confirm
  retention of attempts, failed stages, policy verdicts, and evidence through
  the CLI.
- Operators can plan and digest-confirm recovery of an incomplete local attempt
  from its immutable history/config identity and durable operation journal.
- Direct single-run execution remains independent of planner and history
  availability.

This is the minimum control-plane functionality required by `v1.0.0`.
Schedules, remote executors, leases, and multi-user administration may follow
in `v1.x` after the single-host contracts are proven.

The post-`v0.2.0-rc.2` main branch introduced the first alpha fleet, plan, and
history formats. Current producers now emit stable `v1` identifiers for the
report, drill spec, events, operations, policy evaluation, artifact
references/store, fleet, plan, compatibility matrix, local history, and
attempt-recovery plan/result. The
`v0.3.0-alpha.1` exact-candidate store is the declared history
read-compatibility floor. `history migrate` performs a digest-confirmed,
copy-on-migrate transition that preserves historical files byte-for-byte and
leaves the alpha source as rollback state. Deterministic crash-resumable
history retention and reference-aware local artifact GC are also implemented.

This closes the stable-identifier and backup-safe history-migration
implementation gates. Actual child-process kills also cover migration,
retention, artifact-GC publication recovery, and a disposable WAL-G mutation
boundary followed by owned-target reconciliation and a clean new attempt. GA
still requires repeated exact published-candidate use, broader advertised
compatibility evidence, publication and independent verification of the
implemented signed archive/OCI supply chain, and an external pilot.

### Stable Data Contracts

- Configuration, fleet, plan, local-history, report, event, drill-spec,
  policy-evaluation, operation-checkpoint, artifact-reference, and
  compatibility-matrix formats, plus attempt-recovery plans/results, have
  documented versioning and validation rules.
- Public GA formats use stable version identifiers rather than `v1alpha1`.
  Implemented on main; retained alpha evidence remains read-compatible.
- The final prerelease proves reading and migrating retained reports and local
  history from the documented pre-GA compatibility floor. The frozen fixture,
  byte-preservation checks, interrupted-copy restart, and CLI flow are covered
  locally; the exact published final prerelease must repeat them.
- Strict input and local-state formats reject unknown fields. Durable report
  readers retain their documented additive-field compatibility within a known
  schema version; invalid enums, identity drift, and broken artifact
  references fail explicitly in every format.
- Public CLI, configuration, and schema changes follow Semantic Versioning and
  a documented deprecation policy after `v1.0.0`.

### Distribution And Security

- Release archives remain deterministic, checksummed, and bound to an
  immutable tag and full commit.
- Linux amd64 and arm64 have signed release artifacts; a multi-architecture OCI
  image is available for automation and Kubernetes Jobs.
- Releases include an SBOM and verifiable build provenance.
- Secret values are resolved at the execution boundary and are excluded from
  specs, events, reports, logs, metrics, artifacts, and planner output.
- The repository documents supported-version lifetime, vulnerability
  reporting, upgrade, rollback, retention, and data-removal behavior.

The archive/OCI/SBOM/provenance pipeline and local OCI content verifier are
implemented on `main`. This is an implementation statement, not completion of
the distribution gate: a final candidate must still publish the signed assets,
prove anonymous image access, download them independently, and use those exact
artifacts for the retained compatibility and demo runs.

### Operational And Product Evidence

- The exact GA candidate passes unit, race, workflow, release, all advertised
  provider, and disposable CNPG gates from a clean commit.
- The provider gate includes a real stopped-process recovery case that retains
  the incomplete attempt, proves exact owned cleanup, and passes a new attempt.
- The published artifacts are downloaded independently, verified, and used for
  the final compatibility runs.
- The documented demo can be reproduced from published artifacts without
  source compilation.
- At least one external pilot completes a pre-agreed restore claim and records
  limitations, operator workflow, evidence usefulness, and cleanup outcome.
  Customer-specific data does not need to become public.
- Known limitations and unsupported cells are visible in release notes and the
  compatibility matrix.

## Explicitly Not Required For v1.0

- A browser UI or TUI.
- A hosted or multi-tenant SaaS service.
- Remote executors, cross-site leases, or high-availability controllers.
- An arbitrary workflow DAG or user-provided shell as control-plane logic.
- An external adapter/plugin protocol.
- Support for every PostgreSQL, provider, storage backend, operating system, or
  recovery-target combination.
- A promise that measured demo RTO or RPO applies to customer infrastructure.

These capabilities can be added after GA without weakening the standalone
engine contract. A web UI becomes justified only when real multi-user RBAC,
audit, approvals, and fleet-history workflows exist.

## GA Exit Checklist

`v1.0.0` can be tagged only when all of the following are true:

1. Every required product surface above is implemented and documented.
2. Stable schemas and migration tests replace the prerelease alpha contracts.
3. The advertised compatibility matrix is backed by retained exact-candidate
   reports and contains no inferred support cells.
4. Two consecutive aggregate candidate runs pass without source or metadata
   changes.
5. Signed archives, OCI image, checksums, SBOM, provenance, release notes, and
   upgrade instructions are published and independently verified.
6. The technical demo and at least one bounded external pilot have passed.
7. There are no open release-blocking correctness, data-isolation, secret
   exposure, cleanup, or upgrade defects.

Passing this checklist means pgdrill has a stable supported boundary. It does
not mean every roadmap feature is complete.
